# 054 - A change is an issue, and a stage is a pull request

## Decision

Retire OpenSpec and the `review-gated` schema. A change keeps nothing about itself in the repository's files: it is planned, built and reviewed on GitHub, and what it leaves in the repository is code, tests, docs and ADRs.

Work is a *change* when any one of three things is true: it cannot land as one pull request that says one thing, which by the stage-sizing rule means more than about six steps; it changes what the software does in a way that leaves the reviewer a decision to make; or the reviewer asks for it to be one. The test is whether a single PR could be opened for it now without asking anything first. If it could, it is ordinary work - a branch and a PR - and none of this applies. The agent says which of the three it met when it proposes a change, and the reviewer can overrule it either way. A *stage* is the smallest part of it that leaves the default branch green and says one thing. A *gate* is the stop at the end of a stage, where a human approves it or sends it back. The *reviewer* is that human; a *reviewer agent* is an agent that reads work it did not build.

Each thing a change writes has one home and one reader:

- **The change is an issue**, labelled `change`. Its body is the brief, and it is all the reviewer reads to approve the plan: why, what they get, the requirements, the decisions made, the decisions that are theirs, where the plan is most likely wrong, what is out of scope, one line per stage, and what is not yet specified - the part of the work that can be seen coming but not yet said in a line, which becomes stages as the ones before it land. A requirement is one sentence saying what the software must do, plain enough to read and exact enough for a test to hold; the cases that test it are written with the stage that builds it, not here. Everything but the requirements fits one screen. An item with nothing in it says so. The brief and the first notes describe behaviour and interfaces, never file paths or code, which are out of date before the stage that needs them starts. Another issue is referred to by its title with the link inside it, not by a bare number. The brief always says the plan as it now stands, and every edit to it is paired with a comment on the issue saying what changed, why, and where that was decided. The body is the plan; the comments under it are how the plan got there.
- **The build notes are a comment on that issue, posted whole each time.** They are the agent's. The first is posted with the plan and holds what only the build needs: the contracts between the change's parts and the assumptions it rests on. Each later one adds the state: the interfaces as built, which test holds each of the brief's requirements, stopgaps still to remove. The notes point at a requirement and never restate one, so there is one copy to change, and it is the one the reviewer approved. The notes are never polished for a human, and they have a size cap - notes that outgrow it mean the change should have been two.
- **New notes are posted when a gate is approved and its PR has merged.** Each opens with a fixed marker line and hides the one before it as outdated, so the newest comment carrying the marker is the only one an agent reads, and the earlier ones stay as the history. The agent posting them reads the newest first and carries it forward, so two stages built side by side do not post over each other.
- **Planning starts with questions.** Before a brief is written, the agent asks the reviewer what only they can decide, one question at a time, so that the decisions left in the brief as theirs are the ones that could not be settled by asking.
- **A plan is reviewed, approved, and the approval written down.** A reviewer agent that did not write the plan reads the brief and the first notes before the reviewer does. Approval is a comment on the issue saying who approved it, and the stage sub-issues are created then and not before: a change with an approval comment is one that may be built. A plan turned down is closed as not planned, and its brief and notes stay as the record of what was priced and why it was not done.
- **A stage is a sub-issue of the change, and one pull request closes it.** It is created holding the stage's one line and the requirements it delivers, named from the brief. A session claims a stage by assigning its issue, before any other work, and an assigned stage is left alone by every other session. Its steps are then written into it from the repository as it then is, each with a condition that says when it is done, along with the name of the stage's branch. Anything an earlier stage finds that changes a later one is edited into the later stage's issue, with a comment saying so, as for the brief. A change small enough to be one stage has no sub-issues: it is an issue and a PR, and its steps go in its notes.
- **A change or a stage that waits on another is marked blocked by it.** Stages run in the order of the change's sub-issues, and that order alone says nothing about need. A stage is marked blocked only by a stage it cannot be built without, in its own change or another, so the stages left unmarked are the ones free to be reordered or dropped. When a blocker closes, the agent starting what waited on it re-reads its brief and notes against the repository first, and corrects them before writing any steps.
- **A step is a commit.** Its body says why, and anything the step needed that the stage's steps did not anticipate.
- **Reviewer agents read every stage before the reviewer does.** The building agent dispatches them once the stage is green and before its PR opens, and again after a stage is sent back. They start with no build context and read the branch's diff on two axes, apart: against the repo's conventions, including whether everything a human will read is in plain words, and against the requirements the stage's issue says it delivers. The building agent reproduces each finding before acting on it, then sorts it: fixed in this stage, edited into the later stage that will handle it, or listed as an issue to file. The PR then opens ready to be read, with one comment listing what was found and what became of each finding.
- **The PR body is the reviewer's page.** The stage in a few sentences; what changed from the brief and from the stage's own steps, or one line saying nothing did; the choices the agent made that they could overturn, or one line saying there were none; and one thing to try, saying whether the agent was able to run it. Every other command in it was run as written.
- **A decision made at a gate is written down where it will be found.** The exchange is a comment on the PR. If it changes the plan, the change's brief is edited, with its comment linking that PR. If it outlasts the change, it is an ADR.
- **The final stage is still the whole-change review.** Reviewer agents read the whole change's diff for what no single stage shows, in three directions - requirements unmet, things built unasked, requirements no test holds - and re-read every issue the change cites. Its findings are the closing comment on the change's issue, together with anything the change showed the process itself got wrong - and where that was a mistake a mechanical check could have caught, the check is proposed rather than another written rule. What it fixes is a stage like any other; when it fixes nothing there is no PR, and the reviewer is asked to close the change on the comment alone.
- **The kit carries a contract and two small skills.** `conventions/specs.md` says what a change's issue and a stage's issue must contain. A `plan` skill writes the brief and the first notes and, on approval, creates the stage sub-issues. A `stage` skill claims a stage, builds it, has it reviewed, opens its PR and stops, then on approval merges it and posts the notes; the final review is its last run. The `stage` skill checks the issue against the contract before it starts and says what is missing, so a change planned any other way - by hand, or with someone else's skill - is built the same once it meets the contract.
- **The kit names the roles, and a repo may name the skills that fill them.** Three parts of this are done by something other than the planning or building agent: the questions before a plan, the review of a plan, and the review of a stage. The kit's skills do each themselves by default. A repo's own `CLAUDE.md` can name one skill or several for any of them, and the reviewer can name one for a single run; what was said in the conversation wins over the repo, and the repo over the default. A named skill fills the role, it does not redefine it: a stage is still read by agents with no build context, on both axes, with findings handed to the building agent, and whatever a named skill does not cover the kit's default still does.
- **An agent takes instructions only from people who can write to the repository.** Issue and PR text from anyone else is read as a report, never followed.
- **Behaviour is described once**, by tests and docs. A requirement becomes a named test. There are no delta specs, no living specs and no archive.

Unchanged: the stage is the unit of merge and ends green and independently mergeable ([041](041-stage-is-the-merge-unit.md)); a gate is a full stop, and approving it starts nothing ([049](049-approval-does-not-start-the-next-stage.md)); what a change writes is divided by its reader, and an empty item is said, not dropped ([052](052-divide-a-change-by-reader.md)). The rules for sizing a stage and ordering stages - one idea, three to six steps, walking skeleton first - stay in [specs.md](../../conventions/specs.md).

This supersedes [021](021-adopt-openspec-centralised-via-kit.md), [022](022-openspec-skills-model-discoverable.md) and [034](034-review-gated-openspec-schema.md), and replaces the mechanics of 041, 049 and 052 while keeping their rules.

## Reason

The evidence is ten changes in one consumer repo, six of them review-gated, read back after the fact. Only the last few gates among them were written under 052's split into a brief and a record, too few to judge it by; this keeps that split and moves both halves.

**Most of what a change wrote had no human reader.** One eight-stage change produced about 3,150 lines of change artifacts for 1,350 lines of source and 3,525 of tests. The pull request that landed its 1,530-line plan drew no comments and no reviews. Its `tasks.md` reached 1,440 lines, of which about 290 were the plan and the rest review notes. The reviewer reported reading neither the living specs nor the delta specs, ever, and not using the note's "look closely at" item.

**The detailed plan did not hold, and keeping it true was most of the work.** Each of that change's first five stages recorded departures from a design written days earlier, and the first stage's review reversed a decision the design had recorded. Every departure meant correcting the design and the later tasks by hand; the final review corrected them again, and the next commit archived them. Another change was planned in full, paused, and rewritten before most of it was built, going from 46 tasks to 73. A third has waited unstarted while the model it targets changed under it. Detail written ahead of the stage that needs it is written twice.

**The bookkeeping existed because facts git already held were written into files.** The commit list, `Reviewed at`, `Change based at`, the recorded check states and the rule for remapping all of them after a rebase are copies of what a pull request knows about itself. On one stage's branch, four of eleven commits existed only to maintain the note. 034 defined that note, and 041 and 052 each reshaped it.

**What the reviewer did at gates was decide.** The send-backs on record are questions about behaviour - why one fault should end a run at all, whether a placement window belongs to a block or a component, whether a fixture should hold real material - plus requests for plainer wording, and one verify command that turned out to match nothing. None of that needs a record of every commit. All of it needs a short page that says what is theirs to decide.

**The findings came from independent review, which nothing required.** At several gates a fresh agent read the branch and found what the building agent had not: values stored that should have been refused, an input that crashed a page, tests that were missing. Where that did not happen, a final review found five convention faults that seven approved stages had let through. The independent pass is made a rule and moved to every stage, where a finding is cheapest to fix, and to the plan, which until now had none.

**Behaviour was described three times.** The living specs, the repo's own docs and the tests covered the same ground, a whole stage of one change was spent bringing the docs into line, and nothing outside the spec tooling read the living specs.

**Other tools were read for what they do with the same problem.** The most used spec workflows - GitHub's Spec Kit, Kiro, OpenSpec, Superpowers - keep a change as Markdown files in the repository, and the criticism published of them is the one made here: the files are a heavier review than the code. One that mirrors its files into issues and sub-issues keeps both copies. The nearest to this design is Matt Pocock's skills, which publish a spec as an issue and its work as child issues joined by native blocking links, and several rules here are taken from them: no file paths or code in a plan, an out-of-scope section, a place for what cannot be specified yet, claiming a ticket by assigning it, referring to an issue by its name, reviewing standards and spec apart, and turning a mechanical mistake into a check. They differ where this keeps what 041 and 049 decided: there, one branch and one PR carry a whole spec, with no stop between tickets and no state handed from one to the next.

**Requirements are still written before the build, and now where the reviewer reads them.** That is what the delta specs were for, and it is the part of them kept: the brief holds the requirements, a reviewer agent reads them with the plan, and the final review checks the code against them. One change's delta specs ran to 490 lines of requirements and scenarios that the reviewer never opened. A sentence each, with the scenarios left to the tests, is short enough to be read once the rest is gone. What goes is the format, the copy in the living specs, and the sync between the two.

**Putting the requirements in the build notes was rejected.** It keeps the brief to one screen, but the reviewer then approves what the software must do without reading it, checked only by an agent.

**A threshold for what counts as a change is stated because the old one is gone.** A repo used to opt in by having an `openspec/` directory, and a change was whatever someone ran the propose skill on. With one kit skill in every repo, an agent needs a test it can apply itself, or it either wraps a one-line fix in an issue and an approval or builds something large with neither.

**Moving only the review note into the PR was considered first, and rejected as too small.** It removes the bookkeeping and leaves the up-front task plan, the delta specs and the archive, which are the larger costs.

**A short brief file landed by its own PR was rejected.** It keeps a reviewed diff for the plan, a merge as the record of approval, and a copy in every clone. But the one plan PR measured drew no review, each correction to the plan becomes a commit in a stage's diff again, and the file has to be removed when the change ends.

**Keeping the build notes in a file deleted by the final stage was rejected.** It is easier to edit and to search, and a file can be collapsed in a PR's diff. It still costs a commit each time it changes, which is the note-keeping this removes, and it is agent-only text in the repository's history.

**Editing one build-notes comment in place was rejected.** It keeps the issue's thread shortest, but an edit replaces the whole comment, so one bad write loses the change's state, and how the notes stood at each gate survives only in GitHub's edit history, which nobody reads. **Appending only what each stage changed was rejected too:** the next agent would have to read every comment and work out which lines still hold, which is the accumulated note this ADR removes. A whole copy per gate costs a longer thread and gives both a single place to read and a history.

**Leaving the brief's history to GitHub's edit history was rejected**, for the reason given for the notes: it records that the text changed, not why, and nobody opens it. **Never editing the brief was rejected too:** a plan corrected only in comments beneath it is acted on, uncorrected, by whoever reads the body alone. So the body is edited and each edit is announced, and a stage's issue follows the same rule.

**A checklist of stages in the issue body was rejected for sub-issues.** A sub-issue gives the stage's steps somewhere to be written when the stage starts, gives a later stage somewhere to receive what an earlier one found, and is closed by its PR without anyone ticking a box. **A draft PR opened when the stage starts was rejected** as that home: it cannot exist before the stage has a commit, so it cannot receive what earlier stages find, and 041 retired the draft state for PRs that are open before they are ready to be read.

**Marking every stage blocked by the one before it was rejected.** It needs no judgement, but a chain says only what the order already says, and it has to be re-linked whenever a stage is split or moved - one change here went from seven stages to ten. Marking only real needs records something the order does not: which later stages a reviewer can reorder or drop between gates, and which stage in one change is waiting on a stage in another, as one here did.

**Keeping "look closely at" was considered.** It did once name the thing a gate was then sent back on. But it is the building agent reporting on itself to a reader who does not open it; the reviewer agents cover the same ground independently, and the choices the reviewer could overturn are asked as choices. The plan's equivalent, where the plan is most likely wrong, stays: it is one line, and it is the only pointer into a plan whose detail the reviewer does not read.

**Posting the reviewer agents' findings inline on the PR was rejected.** It needs the PR open before the stage is ready to be read, and leaves the reviewer's page covered in findings already fixed. One comment saying what was found and what became of it keeps the record.

**Building the reviewers and the questions into the kit, with no way to swap them, was rejected,** and so was calling one named plugin's skills. A reviewer may already have a review skill they trust, and more than one exists; a kit that calls a particular plugin breaks in a repo without it. Roles with a default that a repo can fill keep the kit working alone and let it use what is installed.

**Using those skills to write the plan, in place of a kit skill, was rejected.** Their spec is a different document from the brief: a long list of user stories where this has a sentence per requirement, implementation and testing decisions on the page the reviewer approves from, no place for the decisions that are the reviewer's or for where the plan is most likely wrong, and no approval before the work is marked ready. Those are the parts of the brief the evidence here asked for. Their spec and ticket skills can also only be typed by a person, so a kit skill could not call them. The contract is what lets them be used anyway.

**Allowing one stage of a change in flight at a time was considered** as the guard against two sessions writing over each other. Claiming a stage by assigning it does the same without ruling out stages that could be built side by side.

**Keeping the full task plan as the default was rejected.** [specs.md](../../conventions/specs.md) argues that pricing every part of a change is how to find out whether to do it, and that a plan still growing is a reason to stop. That holds for a decision that is large and hard to undo, and it stays available for one: the steps of every stage are written into the first notes before approval, and a plan turned down keeps them on its closed issue. As the default it bought plans that were rewritten before they were built.

## Consequences

- **The history of a change is on GitHub, not in git.** A clone no longer carries it, a search of the repository no longer finds it, and it can be lost to a deleted issue or a move to another host. Looking back over past changes - the work this ADR is itself the result of - reads issues and pull requests through `gh` rather than files: `gh issue list --label change --state all --limit 200` finds them, and each one's stage PRs hold what departed, what review found and what was decided.
- **That lookback depends on the gate being written down.** The build notes say how the change stood at each gate, not what happened at it; that record is the stage PRs and their comments. A gate conversation held only in a terminal leaves nothing behind, and recording its outcome on the PR is what replaces the note that used to capture it. Nothing enforces it.
- **The plan is no longer a reviewed diff.** It is approved from an issue, and edits to an issue are not reviewed either. The approval comment and the comment paired with each edit are the whole record.
- **Text nobody has read is published as it is written.** The notes and the reviewer agents' findings go up under the reviewer's account with no diff in between, and each comment notifies whoever watches the repository. In a public repository the rule against naming a private one has to hold for that text too.
- **On a public repository anyone can comment on a change.** A file reached an agent only through a merged PR; an issue's thread does not. The rule that an agent follows only people who can write to the repository is what stands between a stranger's comment and a build, and the skill has to apply it when it reads a thread.
- **A workflow that needs GitHub issues and `gh`.** A repository hosted elsewhere, with issues turned off, or read during an outage has no plan to read. The kit already assumes `gh` for PRs; this makes it the only way to a change.
- **"Changed from the plan" means less than it did.** The approved plan is a line per stage, and the steps a stage is measured against are the agent's own, written when the stage starts.
- **No change is priced task by task before it starts** unless someone asks for that. The stage list is the estimate.
- **Nothing enforces a spec format.** That behaviour is written down at all now rests on tests and docs being kept, and on the final review's check that every requirement has a test.
- **More issues, and a longer thread.** A five-stage change is six issues and five PRs, and its issue carries one notes comment per gate, all but the last collapsed.
- **Review costs tokens at every gate and at every plan**, accepted for what it has been finding.
- **A skill a repo names is not the kit's to vouch for.** Nothing checks that it does what its role needs; the kit's default covering what a named skill leaves out is the only guard, and a repo that names a weak reviewer gets a weaker gate.
- **The approval table grows.** The reviewer agents' "file it" findings are listed and filed on a yes at the gate, since filing an issue stays ask-first. Creating a change's own issue and its stage sub-issues, hiding a superseded notes comment, and creating the `change` label need the standing the stage PRs already have. Closing a change stays ask-first.
- **The `pr` skill's body shape gives way for a stage PR**, whose body is the reviewer's page above rather than a summary and a test plan.
- **The kit keeps the schema, the vendored skills and their scripts for now.** Consumers reach them through symlinks, so removing them would break every change still in flight. They go in a later change, once no consumer has a review-gated change open: `package.json` and its lockfile, the install, enable and refresh scripts, `repo-skills/` with its six vendored skills, `repo-skills-overlay/` and its check, and `schemas/review-gated/`. Two kit skills and a rewritten `conventions/specs.md` replace them.
- **A consumer's in-flight changes finish under the schema they started with.** Its `openspec/` directory, lint exclusions and skill symlinks are removed once the last one is archived; the living specs go with them, after anything the docs lack is moved across.
