# 074 - The merge hook checks the squash credit lines

## Decision

`hooks/pretooluse-merge-message.py` refuses a `gh pr merge` whose message lacks a `Co-authored-by` line for each commit author who is not the PR's author, the rule `conventions/git.md` calls Squash credit.

- The hook runs when the command gives a subject or a body, since either replaces GitHub's own message. It asks `gh pr view [<PR>] [-R <repo>] --json author,commits,url` for the PR's author and each commit's author login. The PR is the command's selector, or the current branch's when the command names none; a flag's value, in any of the forms `gh` accepts (`-t text`, `-t=text`, `-ttext`, bundled as `-st text`), is never read as the selector. A PR of 100 commits or more may have been cut short by `gh pr view`, so the rest are read from the REST list (`gh api --paginate repos/<owner>/<repo>/pulls/<N>/commits`) and added to what `gh pr view` gave, which includes each commit's trailer co-authors. REST gives only a commit's author, so the hook also reads co-authors named in a later commit's message by their `<id>+<login>` no-reply address, and leaves out `[bot]` accounts, which `gh pr view` gives no login. A login is read only if it is letters, digits and hyphens (with `[bot]`), so commit text can't steer the `gh api` call or the refusal. A co-author of a later commit with another address goes unread. GitHub caps the REST list at 250 commits, so a PR with that many is refused, with the way out: merge it in GitHub's UI, which adds these trailers itself.
- A line counts when it is a `Co-authored-by:` trailer in the message's last paragraph, and every line of that paragraph is a trailer, which approximates how git reads them (a credit directly under `Closes #N`, or after body text with no blank line, is not one; git also takes a mixed paragraph holding a known trailer such as `Signed-off-by`, which the hook does not), whose address is `<id>+<login>@users.noreply.github.com` for that login, whatever name precedes it. Logins compare without regard to case. A commit author with no login needs no line.
- Only a refusal makes a second call per missing author, `gh api users/<login> -q .id`, so the message can spell out the line to add. If that call fails the line carries `<id>`, and the refusal says it is a placeholder to fill in. The line's name is the author's login, not their git name: the name is metadata anyone can set, and the refusal is text an agent acts on. The name is free, as far as the check goes.
- A `Co-authored-by:` line may run past the 72-column body wrap. Its name, login and a nine-digit id can't be wrapped, and without the exemption the hook would demand a line that `conventions.py`'s wrap rule then refused. `commit-msg` shares the exemption.
- In a repo that reaches the kit, a `gh pr merge` the hook can't check is refused: a lookup that fails, runs past 15 seconds (25 for one merge's lookups together), or returns something unreadable or of an unexpected shape, with `gh`'s own error in the refusal; a body the shell rewrites (a `$name`, `$(...)` other than `$(cat <<'EOF' ...)`, a backtick, or an unquoted heredoc holding one), a `--body-file` the hook can't open as UTF-8 text (missing, a path the shell expands, created by the same command) and a `-` or `/dev/stdin` without exactly one heredoc on the merge's own command; a merge that reads its body from a heredoc in a command whose heredoc delimiters the shell lexer and the heredoc scan read differently (an arithmetic `<<$n`, a heredoc the lexer misses after a `#` in a word, a delimiter the scan doesn't read), compared as a sequence so two misreads can't cancel; a payload directory that doesn't exist (a `cd` the hook can't follow, such as `cd "$(...)"` or a missing target, leaves the directory as it was); a repo `git` can't be asked about, because either `git rev-parse` the kit check runs is missing, runs past 10 seconds or refuses the directory (safe.directory), which would otherwise read as "not a kit repo" (a directory that is no repo at all, or a bare repo or `.git` directory, is an answer, not trouble; `git` runs in the C locale so a translated message can't turn one into the other); a command, or a `bash -c` string, whose quoting the shell lexer rejects (an unbalanced quote) that mentions both `gh` and `merge`, since the simple command it gave up in is lost, the refusal saying to balance the quote; a command that may run in more than 8 directories, refused in any repo, since the hook can't tell where its merge runs, and checked before the unbalanced-quote refusal; a merge in a string a shell runs, meaning the string after `bash -c` or the words of `eval`, parsed and searched as a direct command is, so `bash -c 'GH_REPO=x /usr/bin/gh pr merge ...'` is found (a script, or a quoted commit message that only mentions it, is left alone); a merge with a `GH_` or `GITHUB_` variable set on it or exported earlier in the same command, which the hook's own `gh` wouldn't see, the refusal saying to use `-R owner/repo`; and an error anywhere in the check, which the hook catches, because it is registered with `|| true` and a crash would otherwise let the merge through. A subject the shell rewrites skips the message checks (the subject's, the body's wrap and the breaking-change footer), and the credit check still runs. The reviewer fixes the cause and retries the same merge; nothing was pushed, so an approval of the head stands. A cause no retry can cure (a PR of 250 commits or more, a commit list that isn't JSON, a PR author with no login) is said to be so, with the way out.
- `gh` runs without `CLICOLOR_FORCE` and `GH_FORCE_TTY`, which make it colour its JSON, and with `NO_COLOR` and `GH_PROMPT_DISABLED` set.

## Reason

The rule had no enforcement: the merge skill points at it, and a merge that skipped the read landed without credit. PR #190 and PR #222 did, each opened by the bot account with commits authored by a human. A squash commit on the default branch cannot be amended afterwards, so a miss is permanent.

**Why a hook, not CI.** The squash message is written at merge time, after every PR check has run. A workflow on `push` to the default branch could see a missing line, but only once the commit is public.

**Why matching on the login, not the id.** The address's `<id>+<login>` form carries the login, so the check needs no user lookup to decide; the id is fetched only to word a refusal. A merge that passes costs one `gh` call.

**Why fail closed.** A squash commit cannot be amended, so a merge the hook couldn't check is the outcome the hook exists to prevent. This differs from the hook's other checks, which let through a command they can't parse (ADR 047): those read only the command's text, which is always at hand, while this one depends on the network and on a message the hook has to read. The cost is that a slow or signed-out `gh`, or a body written with `$VAR` or an unquoted heredoc, stops a merge until the reviewer fixes it and retries. The refusal for an unreadable body says to pass it with `--body-file -` and a quoted heredoc, the form the merge skill uses. An unquoted heredoc is refused when it holds `$` or a backtick because the shell expands them: the squash body then differs from the text the hook checked.

**Why exempt the credit line from the wrap.** The rule is mandatory and its line is unbreakable, like the URL the wrap rule already exempts. A PR author `bot` and a commit author `christopher-montgomery` with a nine-digit id gives a 98-character line that the hook demanded and then refused, so such a PR could not be merged.

Alternatives rejected:

- **Computing the lines in the skill.** The skill already says to; this is the case where an agent skipped it.
- **A `push`-triggered workflow.** It reports after the commit is public and cannot fix it.

## Consequences

- Every merge through Claude that gives a subject or a body now pays one `gh` call, and a refused one pays a second.
- A merge made in GitHub's UI is outside the hook, as for every other message rule. The UI adds these trailers itself.
- A PR whose commits are all by its own author needs no line, and the hook makes no call beyond the one.
- Some commands are not checked. A `gh pr merge` giving neither subject nor body leaves the message to GitHub, and a flag with no value is left to `gh` to refuse. The hook finds a `gh pr merge` after any words (`FOO=1`, `env`, `command`, `time`, `sudo`, `!`, `{`, `then`, a path to `gh`), across a backslash-newline, and with `-R`/`--repo` before `pr` or `merge`. A backslash that ends the command escapes nothing and is dropped. A `<<WORD` that no later line closes, and one whose word doesn't start with a letter or `_` (`1<<20`, `<<%s`), is not a heredoc. A merge made through `gh api` to the merge endpoint or built from a variable (`$GH pr merge`) is not recognised, and a shell fed on stdin (`bash <<'EOF'`, `echo '...' | bash`) is not read. A `<<` inside a comment, and a command bash accepts but `shlex` reads differently (`$'it\'s'`), can still misread a command. A comment is dropped before the command is split, its newline kept, so a `# note` after a `cd` or after the merge's `<<'EOF'` joins nothing to the next line. The hook follows `cd`, `pushd` and `popd` through `-P`, `-L`, `--`, `builtin`, `command`, a variable set on it, and `if`, `elif`, `while`, `until`, `{`, `then`, `do`, `else` and `!` before it, expanding `~`, `$HOME` and `$PWD` (the tracked directory, not the hook's own) and tracking real paths so two routes to one directory are one. Where it can't tell which directory a command runs in it checks the merge in each it might be in: a `cd` in parentheses, a pipeline, a backgrounded list (`a && b &`) or a group (`{ }`, `then`, `do`), which may run in a subshell or not at all; `cd -` and `$OLDPWD`; a `pushd` or `popd` it can't follow (`pushd` with no argument, `-n`, `+N`, `-N`); and a target `expanduser` rejects. A `pushd` that fails pushes nothing, `pushd .` succeeds, and one in a subshell leaves the stack alone. A `cd` to a directory that isn't there or to a target with an unset variable or `$(...)` changes nothing. More than 8 possible directories refuses the merge, counting those the command might be in, not those it has been through. A conditional `cd` (`[ -d x ] && cd x`) is followed as if it ran, a `)` that ends a `case` pattern reads as the end of a subshell, and a parse failure stops the tracking at the failure. `..` after a symlink resolves to the real parent, where bash's `cd` resolves it logically (`cd -P` aside), as the `git` the hook runs there does; `cd .fieldkit/..` from a consumer is judged in the kit's parent. A merge inside a quoted command substitution (`x="$(gh pr merge ...)"`) is not found. `git -C` moves only that `git` command, so it needs no following. A `<<EOF` inside a quoted string that a later line closes still reads as a heredoc and hides what lies between. The hook guards against an agent skipping the rule, not against a determined bypass. Issue #228 weighed closing more: the gaps an agent can hit by accident (the directory tracking, the parse failure, `git` failing, a comment after a `cd`) are closed above, and the rest each need a deliberate command shape, not the merge skill's `gh pr merge ... --body-file -`, so they are accepted. Refusing every command that mentions both `gh` and `merge` was rejected: it would stop any echo or commit message that names a merge.
- A body the hook refuses as unreadable adds friction where a literal `$` is meant (`--body 'costs $HOME'`), and a command that only mentions `bash -c 'gh pr merge ...'` is refused too. The refusal says how to pass it. A PR of 250 commits or more can't pass the hook at all, and the refusal says to merge it in the UI.
- This ADR narrows two earlier ones: [047](047-enforce-commit-messages.md), which let a merge with no `--subject` through, now checks credit on a body alone; and [062](062-a-push-voids-merge-approval.md), whose `=` caveat for `--match-head-commit` no longer applies.
- The hook and `conventions.py` must stay importable on Python 3.9, which macOS's system `python3` is: an import error under `|| true` would let every merge through, so annotations such as `str | None` sit behind `from __future__ import annotations`, and a test pins it.
- The hook needs `gh` on the PATH and signed in, which the merge skill needs already. Without it the merge is refused, not let through.
- A merge command that names a PR `gh` can't find is refused by the hook before `gh pr merge` would have refused it. The outcome is the same.
